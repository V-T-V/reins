# 当 AI 开始替你重启服务器：给运维代理立一道"操作前必读"

2026 年，AI 代理写代码已经不新鲜了。它们改配置文件、跑测试、提交 PR——但有一类操作，直到最近我都不太敢交给它们：**对生产机器按下回车**。

重启一台 kiosk 机上的服务、清一个目录、改一条定时任务——这些操作有个共同点：**正确的时机和方式，往往不在命令本身里，而在人的脑子里**。"营业时段别杀壳进程"、"部署要排除 runtime 目录"、"这台机器的防火墙规则别动"——这些约束你会在同事交接时反复叮嘱，但 AI 代理看不见。

我维护着一小队 Windows/Linux 机器。从今年 7 月起我写了一个开源的远程运维平台 [Reins](https://github.com/V-T-V/reins)（Go 单二进制，Agent 反向 WebSocket 出站连接，被管机器零入站端口）。写到第四个月，我在一次部署会话里第 N 次向 AI 助手重复同样的叮嘱之后，决定把这件事变成代码——**不是提示词，是执行层的门禁**。

## 提示词约束为什么不够

"你可以在系统提示里写规则啊。"——可以，而且我写了。但提示词约束有三个结构性弱点：

1. **它可以被说服。** 上下文越长、任务越急，"这次例外一下"的说服成本越低。提示词注入攻击的本质就是这个：规则住在语言层，语言层的一切都可以被更长的语言覆盖。
2. **它不与标的绑定。** 提示词里的规则针对"这台机器的这个项目"，但代理换一个会话、换一个上下文窗口，规则就蒸发了。规则应该住在**它约束的东西旁边**，而不是住在模型的一次对话里。
3. **它没有失效机制。** 规则改了，旧提示词还在历史记录里生效。没有"规则变更即旧授权作废"的语义。

我想要的机制是：规则**随项目仓库走**，AI 操作前**必须先读它**，读完拿到一个**内容指纹**，执行层校验指纹——指纹不对，任务根本到不了机器。

## .reins/rules.md：四层实现

被管理的项目在自己仓库根放一个 `.reins/rules.md`：

```markdown
# loan-kiosk-platform 运维规则

1. 勿在营业时段(9:00-18:00)杀壳进程 YxLoan.exe——用户可能正在使用
2. 部署镜像同步必须排除 runtime/ node_modules/ .env(远端运行态数据)
3. 重启壳用 Register-ScheduledTask(-LogonType Interactive 落桌面会话),
   不要用 schtasks /create(被命令策略拦截)
4. 健康检查 http://localhost:3100/health 连续 3 次通过才算部署成功
```

这些不是我编的示例——第 1-4 条来自真实的部署会话，每一条背后都是一次踩坑（第 3 条的坑：`schtasks /create` 被命令策略黑名单拦下后，AI 手工摸索了三种写法才找到正解——现在正解直接写在规则里）。

工作流是四层：

**① 读**。`reins rules read -a <agent>` 自动发现 agent 上各项目的规则文件，打印全文并缓存 ack。AI 代理把全文读进上下文——这一步不可跳过，因为下一步要校验的指纹只有读了才有。

**② ack**。ack 是规则内容的 SHA256 前 16 位。多项目同机时，接受"组合指纹"或任一单项目指纹——AI 读了自己项目的规则就可以操作，不被同机其他项目卡死。

**③ 执行层校验**。agent 开启 `rules_gate: true` 后，所有变更类任务（powershell/script/浏览器自动化/GUI 点击/自更新/电源）必须携带有效 ack：无 ack 拒绝，过期 ack 拒绝，拒绝信息**不回显指纹**——这是防"跳过阅读直接重放"的关键设计：攻击者（或偷懒的代理）拿不到正确的指纹值，就无法伪造 ack。

**④ 变更即失效**。规则文件改了一个字，旧 ack 立即作废，任务被拒并指引重新 `rules read`。发现范围 30 秒缓存——规则改了半分钟内生效。

## 攻击者视角的自测

这套机制写完，我用"恶意代理"的思路测了它：

- **不读规则直接执行** → 拒绝，错误信息指引先 `rules read`。✅
- **读一次，拿到 ack，然后无视新规则** → 改规则文件后旧 ack 失效，同一命令被拒，必须重读。✅
- **从错误信息里套指纹** → 拒绝信息只有"规则已变更，请重新读取"，没有指纹值。✅
- **读 A 项目的规则去操作 B 项目** → 组合指纹语义下允许（刻意的设计取舍：同机多项目时严过卡死误伤，隔离靠 allowed_roots 与命令策略分层）。
- **绕过任务协议** → 诚实边界：`file upload`/`sync` 走流式传输通道，不在门禁内（文档明写）；批量 tag 路径暂不携带 ack（roadmap 项）。门禁不假装自己是万能的。

## 为什么门禁必须在执行层

同样的逻辑，放在提示词里叫约束，放在执行层才叫**闸**。

区别在于失败模式：提示词被绕过时，错误发生在生产环境里；执行层拦截被绕过时——它不被绕过，因为**校验者和执行者是同一个进程**。AI 代理可以给出一万个理由，agent 只认指纹。这不是不信任 AI，这和"数据库不信任应用代码、要求预编译参数化查询"是同一种工程思维：**把约束放进系统，而不是放进对话**。

有个细节我认为值得一提：CLI 在项目目录内执行变更命令时，会把 `.reins/rules.md` 全文自动打印到 stderr——恰好是 AI 代理的上下文通道。也就是说，这个设计不是"防 AI"，是"喂 AI"：规则以机器可执行的方式存在着，同时以自然语言的方式被读到。缰绳的两端都握着。

## MCP 时代：换客户端，不换闸

上个月我补齐了最后一块：[MCP Server](https://github.com/V-T-V/reins/blob/main/docs/mcp.md)。Claude Desktop、Cursor 这类客户端现在可以原生调用 14 个运维工具（`reins_run_command`、`reins_batch_run`、cron 族……）。

于是一个问题变得尖锐：AI 客户端越来越多、越来越能干，规则门禁会不会成为"又一个要单独配置的东西"？不会——因为门禁在**执行层**（agent 侧），不在任何客户端里。CLI、Go SDK、MCP，三种接入方式撞的是同一道闸。你在 Claude 里让 AI 重启服务，和你自己在终端里敲命令，过的是同一个校验。

**接入层可以百花齐放，缰绳只有一根。**

## 写在最后

Reins 是 MIT 开源的（[GitHub](https://github.com/V-T-V/reins)），这套规则门禁没有 Pro 版、没有付费墙——它就是这样一个朴素的信念：

> 当我们把回车键交给 AI，应该同时交出一套它必须先读的规则。规则写在项目里，指纹握在门禁上，缰绳在你手里。

AI 运维代理这条路上，提示词工程是缰绳的影子，执行层门禁才是缰绳本身。
